## Task
Make ProfileFinder's results trustworthy and clear for a 100-row Bulk run: show only relevant sources, avoid wrong people and dead or stale LinkedIn links, and present the results table (screen, CSV and Excel) so a non-technical reader instantly understands each row. Do not change anything that already works.

## Context
- Product: company website + job title → the real person holding that role, with a working LinkedIn URL.
- Tech stack: React 18 + Vite + TypeScript strict + Tailwind v4; Netlify Functions v2 (Node 22); Supabase (Postgres, RLS, Auth); Serper for search; Claude (`claude-haiku-5-5`) via the Netlify AI Gateway.
- Where the relevant code lives: `shared/` (pipeline, decision, corroboration, profileQuality, extractHolder, linkedinUrl, queryBuilder), `netlify/functions/` (`search.ts`, `_lib/*`), `src/lib/bulkRunner.ts`, `src/lib/csv.ts`, `src/lib/xlsxExport.ts`, `src/pages/Bulk.tsx`, `src/components/ResultCard.tsx`, `src/components/VerifiedHolderCard.tsx`.
- Live: https://profilefinder-hristo.netlify.app (Netlify site `profilefinder-hristo`); every push to `main` on GitHub `hristowork14-alt/profilefinder-app` auto-deploys in ~30 s.
- Background: the owner's boss tested the app and said: "The accuracy needs work for sure — it cites some sources that aren't relevant." He will now test Bulk at full capacity (100 rows). No concrete failing examples exist, so the first job is to find the weak spots yourself.
- Facts about the current state you must respect:
  - Bulk is limited to 100 rows per file (`MAX_BULK_ROWS`), runs 2 rows at a time (`BULK_CONCURRENCY`), and can be resumed.
  - Per-account limit `MAX_SEARCHES_PER_HOUR` is currently 30 — a 100-row file cannot finish in one hour under this limit. The plan must address this explicitly (see Requirements 7).
  - Verification decisions: `verified_profile`, `verified_no_profile`, `contradicted`, `unverified`, `no_results`.
  - A human check (Cloudflare Turnstile) now protects sign-up, log-in and password reset, and Supabase CAPTCHA is ON. A site-key problem was just fixed. Do not touch this; only re-verify at the end that log-in and sign-up still work.

## Requirements
1. **Find the weak spots first (before changing code).** Review how `sourceLinks` / evidence links and "Verified by N independent sources" are chosen and shown. Using the existing mocks/fixtures and tests, list concrete failure modes: sources that mention the company but not the person, sources that mention the person but a different company or an old role, aggregators/directories/people-search spam pages, generic company pages, duplicate sources from the same site counted as "independent", and links with an empty or misleading title. Write the findings into the plan.
2. **Source relevance.** Only show a source link if the page demonstrably supports the claim: it names the person AND the company (or its domain) AND the role or a close synonym. Otherwise drop it from the displayed list and from the "N independent sources" count. Count independence by registrable domain (one site = one source). Show at most a few of the strongest sources, each with a short, honest reason (e.g. "names X as CEO of Y"). If no source qualifies, show none rather than a weak one. Keep the existing decision outcomes working.
3. **Wrong person.** Strengthen the checks that prevent returning someone who is not the current holder: former/ex/previous/interim/"former CEO" wording, a different company with a similar name, namesakes, role held at a subsidiary or parent, and conflicting holders across sources. When evidence conflicts, prefer `contradicted`/`unverified` with a plain-language reason over a confident wrong answer. Never invent a person or a LinkedIn URL.
4. **Dead / stale / wrong LinkedIn links.** Never fetch, scrape or log in to linkedin.com, licdn.com or lnkd.in (hard rule — use only what search results and snippets already provide). Within that rule: normalise URLs to the canonical `/in/<slug>` form, reject non-profile URLs (company pages, posts, jobs, pulse, localized duplicates), detect snippet signals that a profile is unavailable or belongs to a different person, and prefer the profile whose snippet matches the company and role. If activity cannot be confirmed, say so honestly (e.g. "Link not checked live") instead of implying it works. Do not add a new paid service.
5. **Results table clarity.** Redesign the Bulk results table and the Excel/CSV exports so each row answers at a glance: Who (name), Role, Company, LinkedIn link (clickable), a plain-language status, a short reason/confidence note, and the best source. Use consistent wording for every status (a short legend on screen and in the Excel file), put problem rows (no result, unverified, contradicted) in a clearly separate or filterable group, keep the original input row number so the user can match results to their file, and make it printable/readable (column widths, wrapped text, frozen header, filters). Add a summary at the top (counts per status). Keep existing Excel sheets "Results" and "All matches" working; improve, do not break.
6. **Bulk at 100 rows.** Make a full 100-row run reliable and understandable: clear progress (done / remaining / failed), automatic retry of transient failures with a handled error path and timeout on every external call, no duplicate spend on repeated companies (reuse the existing cache), safe resume after closing the tab, de-duplication or warning for repeated rows, and a clear message for rows that fail. Estimate and show how long 100 rows will take.
7. **Limits and cost.** Propose (in the plan, for approval — do not change silently) how a 100-row run fits the hourly search limit, Serper credit use and Claude cost: e.g. raising `MAX_SEARCHES_PER_HOUR` via Netlify env, or a separate bulk allowance. Report the expected cost of one full 100-row run before any large live run. Ask the owner before spending credits on a live test larger than ~15 rows, and before changing any plan or spending limit.
8. **Tests and real checks.** Add regression tests for every fixed failure mode (TDD: failing test first). Use company-agnostic fixtures — no company-, person- or domain-specific code or special cases anywhere.
