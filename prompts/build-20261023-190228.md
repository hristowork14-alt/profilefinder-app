# Switch ProfileFinder to real search (real people, working LinkedIn URLs)

## Task
Make ProfileFinder return the **real person currently in the position searched for**, with a working public LinkedIn profile URL that came from real web search results. Do this by running the existing real pipeline (Supabase + Serper + Anthropic) against live services. Run it locally with `netlify dev` first, then deploy it to Netlify. Tune only what real data shows is wrong, and leave everything else in the app exactly as it is.

## Context

### Tech stack (already in place, do not swap anything out)
- Frontend: React 18, Vite 8, TypeScript (strict, `noUncheckedIndexedAccess`), Tailwind CSS v4, React Router 7
- Backend: Netlify Functions v2 (`export default async (req: Request, context: Context) => Response`), Node 22, esbuild
- Database/auth: Supabase (Postgres + Auth), using the new key format: `sb_publishable_…` in the browser, `sb_secret_…` only on the server
- Web search: Serper.dev (`POST https://google.serper.dev/search`)
- Ranking: Anthropic SDK, model `claude-haiku-5-5`. It is called with `output_config: { effort }` because these models reject `temperature`. A deterministic heuristic ranker is the fallback.
- Validation: zod. Tests: Vitest (88 passing). Lint: ESLint flat config. Format: Prettier.

### Why every result is fictional today
The user has only ever run **demo mode**: `npm run dev:demo`, which sets `VITE_DEMO_MODE=true`, or the published demo artifact. In demo mode the whole backend runs in the browser (`src/lib/backend/demoBackend.ts`) and always uses `shared/mocks/`. Those mocks build six seeded, fictional people per company+role, with LinkedIn slugs starting `pf-demo-`. That is why every name is invented and every LinkedIn link 404s.

The **real** path already exists, is unit-tested with mocked `fetch`, and has **never run against live services**:
- `src/lib/backend/supabaseBackend.ts`: real frontend backend (Supabase auth + calls to Netlify functions)
- `netlify/functions/search.ts` calls `shared/searchService.ts → performSearch`
- `netlify/functions/_lib/runtime.ts → createPipelineDeps(env)`: picks real or mock dependencies (`USE_MOCKS=true` means mocks)
- `netlify/functions/_lib/serper.ts`: Serper adapter
- `netlify/functions/_lib/anthropicClient.ts`: Claude adapter
- `netlify/functions/_lib/companyResolver.ts`: fetches the company homepage to read its name. It is hardened: blocks linkedin.com, licdn.com and lnkd.in even through redirects, rejects IP addresses, caps redirects and size.
- `netlify/functions/_lib/{auth,cache,rateLimit,persist,store,supabaseAdmin,env}.ts`

So the job is: **turn on real mode, verify it live, and fix what real Google/LinkedIn data reveals.** It is not a rewrite.

### Pipeline (single source of truth, used by both real and demo modes)
`shared/searchService.ts → performSearch`: validate → bulk-job ownership → 7-day cache → hourly rate limit → pipeline → save → cache write

`shared/pipeline.ts → runSearchPipeline`:
- `DEFAULT_TIMING`: total 9000 ms, homepage 3000, search 4000, LLM 5000, minimum LLM time 1500
- Steps in order:
  1. Homepage fetch and domain query run in parallel.
  2. `shared/companyName.ts → resolveCompanyName` picks the company name.
  3. `shared/queryBuilder.ts → buildNameQueries` builds the name queries: company + position, and company + first synonym.
  4. `filterAndDedupe` cleans the hits.
  5. `shared/rankWithClaude.ts` ranks them, falling back to `shared/heuristicRanker.ts → rankHeuristically`.
  6. `shared/rankingSchema.ts → parseRankingResponse` checks the result: zod plus a **URL whitelist**, so every returned URL must be one of the candidate URLs.
- `shared/linkedinUrl.ts → normalizeLinkedInProfileUrl`: accepts only `/in/<slug>` with an optional locale segment. It decodes and lowercases the slug, re-encodes it, and rebuilds `https://www.linkedin.com/in/<slug>`.

### Places where real data may break assumptions
These are hypotheses to check against captured real responses. Do not assume they are broken.
1. **Domain query yield:** `buildDomainQuery` sends `site:linkedin.com/in "stripe.com" "CFO"`. Real profiles rarely contain the bare domain, so this query may return almost nothing, which makes the name queries the real signal. Check how many useful hits each of the 3 queries actually brings.
2. **Company name resolution:** `resolveCompanyName` / `decodeHtmlEntities` and `companyResolver.ts` must produce the name people use on LinkedIn ("Stripe", not "Stripe | Financial Infrastructure to Grow Your Revenue"). Watch real homepages that block bots, need JavaScript, redirect to a locale, or use `og:site_name` badly.
3. **Real Google title and snippet formats:** `heuristicRanker.ts → parseLinkedInTitle` and the prompt in `rankWithClaude.ts` (`buildRankingPrompt`, `SYSTEM_PROMPT`) must handle the real variants:
   - `Name - Title - Company | LinkedIn`
   - `Name – Company | LinkedIn` (en dash, no title)
   - `Name - Company | LinkedIn`
   - titles cut off with `...`
   - localized titles
   - snippets like `Experience: X · Education: Y · Location: Z · 500+ connections`
4. **Former holders and stale index:** Google often shows an old headline. Check `mentionsFormerRole` and the Claude prompt against real phrasings ("ex-", "Former", "Previously", date ranges like "2019 – 2023").
5. **Same-name or look-alike companies:** check `looksLikeOtherCompany` against real collisions, such as generic names or the same name in different countries.
6. **URL normalization on real URLs:** check that the normalized URL still opens the same profile for:
   - country subdomains (`bg.linkedin.com`, `uk.linkedin.com`)
   - trailing slashes and `?trk=` / `?originalSubdomain=` parameters
   - percent-encoded **non-ASCII slugs** (Cyrillic, accented Latin; important for Bulgarian companies)
   - uppercase in slugs
   - extra path segments (`/in/slug/details/experience`), which are rejected today
   - legacy `/pub/` URLs, also rejected today

   Decide from real data whether any of these needs handling. Never output a URL that wasn't in the search results.
7. **Search locale:** `serper.ts` sends no `gl`/`hl`, so results default to Google US. Only if real tests on non-US companies (for example Bulgarian ones) show missing people, add **optional** `SERPER_GL` / `SERPER_HL` env vars. When they are unset, the request must be identical to today's.
8. **Time budget:** measure real Serper and Claude latency. If the heuristic fallback fires often because of time, adjust `DEFAULT_TIMING` with evidence. Netlify's synchronous function limit is 30 s, but the target stays under 10 s.
9. **Credits:** each single search makes up to 3 Serper queries and 1 Claude call. Bulk CSV uses the same path. Serper's free tier is 2,500 queries. Keep the 7-day cache and `MAX_SEARCHES_PER_HOUR` (default 30) working.

## Requirements
1. With `VITE_DEMO_MODE` unset (or `false`), `USE_MOCKS` unset (or `false`) and real keys present:
   - signing up and logging in works against the user's real Supabase project
   - a search goes `netlify/functions/search.ts` → Serper → Claude (or the heuristic fallback) → saved in Supabase → shown in the existing UI
2. For a company and position, the top result is the person who **actually holds that position now**, as far as public search results allow. Their LinkedIn URL must:
   - come from the Serper results for that search (after normalization)
   - open that person's live profile when a human clicks it
3. Former holders, people at other companies, non-profile URLs (`/company/`, `/posts/`, `/pub/dir/`, `/jobs/`) and people in different roles must not be presented as the match.
4. When the search finds no credible match, the app shows the existing "no results" state. It must never show a wrong person with high confidence. Confidence scores and reasons must honestly reflect uncertainty, including a stale index or a missing title.
5. Every improvement is **general**. No hardcoding of specific companies, people, domains or answers anywhere.
6. Demo mode keeps working exactly as today (see Constraints).

### Hard rules
These come from the original spec and stay binding:
- **Never fetch, scrape, crawl or log in to linkedin.com** (or licdn.com or lnkd.in) in any form: not from the app, not from scripts, not from tests, not even to "check a URL is live". Only search-API results may be used. A human checks links by clicking them. LinkedIn's terms forbid automated access, and LinkedIn answers bots with HTTP 999, so automated checks would be unreliable anyway.
- **Never invent or rebuild a LinkedIn URL.** Every returned URL must trace back to a URL in that search's Serper results.
- **No secret in the browser.** Only `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` may have the `VITE_` prefix. `SUPABASE_SECRET_KEY`, `SERPER_API_KEY` and `ANTHROPIC_API_KEY` are server-only.
- **Secrets never go in code, commits, logs, test fixtures, screenshots or chat output.** Keys live in `.env`, which is already git-ignored (check it still is), and in Netlify environment variables. Logs never print keys, auth headers or full Serper/Anthropic response bodies.
- **Privacy:**
  - Store only what the privacy page lists: name, public headline, public LinkedIn URL, confidence, reason. No emails, phones or other personal data.
  - Raw captured search responses contain real people's data, so they live only in a git-ignored local folder (`.debug/`, add it to `.gitignore`) and are deleted at the end.
  - Test fixtures built from real responses must replace real names and slugs with fictional ones but keep the exact format: punctuation, separators, encoding, structure.
- TypeScript `strict`; no `any` without a justifying comment; no new lint suppressions without a reason comment.
- Every external call keeps a timeout and a handled error path. The UI only ever shows human-readable messages.
- No payments, subscriptions or credits system.

### Follow
- **TDD for every logic change in `shared/`:** first write a failing test from an anonymized real-format fixture, confirm it fails, fix it, confirm it passes.
- Keep the adapter pattern. A new search provider would be a new file implementing `SearchProvider` plus a `case` in `searchProvider.ts`, but don't add one unless Serper provably can't do the job.
- Prettier settings: singleQuote, printWidth 140, trailingComma all.

### Avoid
- Special-casing companies or people
- Lowering confidence thresholds just to show "something"
- Adding new npm dependencies without a reason
- Changing the model or provider without measured evidence
